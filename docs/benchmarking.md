# Benchmarking

Benchmarks prove the skill produces measurably better scenes than naive,
unstructured "dump some primitives" output, not just a single pretty render.

## Run

```bash
python benchmarks/runners/run_benchmarks.py --list
python benchmarks/runners/run_benchmarks.py --profile balanced --tasks product_hero_watch
python benchmarks/runners/run_benchmarks.py --baseline          # skill vs naive contrast
python scripts/visual_review_pack.py --out artifacts/visual_review_pack --allow-unreviewed
python scripts/blind_visual_eval.py --out artifacts/blind_visual_eval --allow-unreviewed
python scripts/visual_review_pack.py --out artifacts/visual_review_pack \
  --human-review artifacts/visual_review_pack/human_review.json \
  --require-human-signoff
python scripts/blind_visual_eval.py --out artifacts/blind_visual_eval \
  --human-review artifacts/blind_visual_eval/blind_review.json \
  --require-human-signoff
python scripts/assert_visual_acceptance.py \
  --visual-review artifacts/visual_review_pack/visual_review_pack.json \
  --blind-eval artifacts/blind_visual_eval/blind_visual_eval.json
python scripts/run_prompt_scenarios.py
python scripts/run_prompt_scenarios.py --render --out artifacts/prompt_scenarios_final_render
python scripts/run_prompt_scenarios.py --live-runs --runs watch_live_agent_forward_v6_20260604 --render --out artifacts/live_watch_final_after_docs
python scripts/run_prompt_scenarios.py --live-runs --runs reference_match_live_agent_forward_v12_20260604 --render --out artifacts/live_reference_match_final_after_docs
python scripts/run_prompt_scenarios.py --live-runs --runs shader_texture_live_agent_forward_v6_20260604 --render --out artifacts/live_shader_texture_final_after_docs
python scripts/run_prompt_scenarios.py --live-runs --runs turntable_animation_live_agent_forward_v2_20260604 --render --out artifacts/live_turntable_animation_final_after_docs
```

Results are written to `benchmarks/results/<task>.json` and `summary.json`.
Benchmarks require Blender because they render. The review-pack command turns
those results into `visual_review_pack.md`, `visual_review_pack.json`, and
`contact_sheet.png` so maintainers can inspect actual previews instead of
trusting a score line.

Prompt scenarios are a separate acceptance layer. They load realistic prompts
from `benchmarks/prompt_scenarios/`, resolve the candidate recipe artifact, and
validate that artifact against static anti-slop gates before optionally running
the same real Blender task checks with `--render`. Current scenarios are marked
`prompt_fixture`, not `live_agent`; they prove prompt-shaped artifacts and real
render gates, not independent fresh LLM generation. Archived live-agent runs in
`benchmarks/live_agent_runs/` are separate forward tests and must keep their own
provenance boundary. See `docs/prompt-scenario-evals.md`.

The review CLIs require explicit visual signoff by default. Use
`--allow-unreviewed` only to generate an automated evidence packet; that packet
is not a final taste approval. For release acceptance, `human_review.json` must
include one approved review per task with 1-5 ratings for `identity`,
`composition`, `material_craft`, `detail_read`, and `ship_readiness`. The
reviewer can be a maintainer, external artist, or explicitly named Codex visual
review agent; do not label agent review as external human review. Any missing
review, unapproved task, or rating below 4 fails the pack.
Run `scripts/assert_visual_acceptance.py` on the generated JSON manifests before
claiming release acceptance. It rejects `human_review_required: false`, failed
packs, missing embedded review proof, and too few reviews.

The blind eval packet is stricter for taste review. It hides task ids, scores,
and task-named preview paths from the public packet, copies previews to
`blind_previews/BVR-*.png`, and writes the task mapping only to
`private_mapping.json`. For release acceptance,
`blind_review.json` must approve every blind item with 4/5 or better ratings
for `prompt_fit`, `visual_quality`, `composition_camera`, `material_lighting`,
`detail_precision`, `anti_slop`, and `ship_readiness`.

Reference tasks may include `reference_image`, `require_reference_image`,
`min_reference_ssim`, saliency/edge IoU gates, coverage/center drift gates, and
brightness/contrast drift gates. The runner then compares the preview against
the actual image file instead of using a neutral SSIM value. SSIM and palette
similarity are not sufficient by themselves; task-specific named-part,
visibility, material, detail, and reference-spatial gates must still reject
visually plausible but semantically empty outputs.
The `reference_match` benchmark uses a deterministic 480x270 PNG generated by
`python scripts/generate_reference_assets.py`; tiny placeholder references are
not acceptable evidence for production-grade reference fidelity.

## Modes

- `skill_plus_tools` runs the task's structured skill recipe through Blender,
  inspects, lints, scores, and validates web export when requested.
- `baseline_no_skill` (`--baseline`) runs the task's naive recipe: bare
  primitives, no camera/lights/materials. It should fail for contrast.
- `adversarial_slop_*` (`--baseline` when a task defines
  `adversarial_baselines`) runs plausible but weak scenes with camera, lights,
  materials, and keyword-heavy names. These must fail; if they pass, the gates
  are too weak.
- `prompt_fixture_plus_render` (`scripts/run_prompt_scenarios.py --render`)
  validates prompt-shaped candidate recipe artifacts, then runs the matching
  Blender task checks. It must not be described as a live model/provider eval
  unless the scenario provenance is `live_agent` and the raw generation metadata
  is archived.

## Tasks (14)

`architectural_interior_scene`, `product_hero_watch`, `sci_fi_corridor`,
`mechanical_exploded_view`, `web_scroll_hero`, `low_spec_laptop_safe`,
`organic_soft_surface_study`, `particle_vfx_energy_burst`, `reference_match`,
`shader_texture_material_study`, `turntable_animation`, `scene_repair`,
`glb_web_budget`, `camera_expensive`.
Pass criteria are in `benchmarks/rubrics/pass_criteria.md`.
The organic/soft-surface task now requires a cohesive fluted hero body plus
smooth curved petal, leaf, and fold mesh details; separate sphere blobs and
beveled cuboid markers are intentionally rejected by named-part, face/modifier,
smooth-object, and `min_curved_detail_objects` gates.
The cinematography task rejects default "expensive" spheres by requiring an
authored faceted hero body, visible catchlight details, material variation, and
an adversarial keyword-heavy sphere baseline that must fail.
The VFX task requires inspected Blender particle systems, emissive shader
families, and directed `create_energy_burst_streaks` ribbon geometry; manual
spark objects alone do not satisfy it.
The visual review pack also detects repeated preview style clusters. If many
unrelated tasks collapse into the same dark/blue glossy language, the pack
fails even when per-task numeric scores pass.
It also checks preview-level artist-quality signals such as contrast and
edge/detail density so a flat single-color render cannot pass just because the
scene graph has named objects.
High-risk tasks also use named-part visibility gates such as
`min_distinct_named_part_objects`, `min_named_part_object_coverage`, and
`min_named_part_total_coverage`; these reject keyword-stuffed one-object scenes
and microscopic named markers that do not make a meaningful visible
contribution.
Craft-detail tasks also use `min_craft_detail_objects` and
`require_craft_roles` so product labels, decals, cables, screws, panel seams,
and grilles must be authored as structured Blender detail (`FONT`, `CURVE`, or
tagged mesh objects), not implied by object names or generic marker cubes.
Geometry-node tasks use `min_geometry_detail_objects` and
`require_geometry_detail_roles` so a procedural benchmark cannot pass with only
a named node group. The inspected scene must expose recipe-specific generated
visual objects such as `panel_wall_plate`, `cable_curve`, `orbital_ring`, or
`bolt_head`.
Shader/material tasks can require `min_subject_material_link_count`,
`min_rich_linked_subject_materials`, and
`require_subject_material_node_name_substrings`. These gates inspect assigned
subject materials, not unused materials, and reject scenes that mention glass,
labels, metal, or texture without linked node graphs and authored shader
subgraphs.
The v32 geometry gates extend that rule to procedural scene work: corridor
benchmarks must expose generated `panel_wall_plate` details from inspected
Geometry Nodes recipe output, not just a node group with a plausible name. The
v30/v31 gates extend the same anti-slop principle to close-surface work: organic and VFX tasks
must expose `surface_microdetail`, `organic_surface`, and `energy_streak` craft
roles, and the shader/material benchmark requires declared image texture roles
such as `base_color` and `displacement`. This catches scenes that have attractive
lighting but no real shader texture craft, micro-relief, or authored surface
precision.
Named-part visibility checks count visual `MESH`, `CURVE`, and `FONT` objects;
face and modifier budgets still apply to mesh geometry.
The scene linter rejects non-intentional detached hero anatomy, such as labels,
caps, buttons, lenses, straps, and nozzles floating away from the body. It does
not treat reflections, highlights, shadows, or material swatches as attachment
parts.
Interactive web benchmarks require a generated camera path with segments,
multiple sampled positions, and meaningful first-to-last movement.
Animation benchmarks also inspect sampled start/mid/end frame transforms. The
turntable task requires enough keyed objects to show real sampled rotation, and
the scroll hero requires the active Blender camera itself to be keyframed with
meaningful sampled camera movement. This rejects actions or GLB clips that exist
technically but leave the scene visually static.
The v34 animation gate goes one step further: it renders start/mid/end proof
frames and compares the images. `require_animation_frame_proof`,
`min_animation_frame_delta`, and `min_animation_changed_pixel_ratio` reject
animations whose keyframes exist but whose rendered frames barely change.
Turntable assemblies must visibly orbit around a shared center, and scroll
heroes must keep a readable first-frame composition while still moving the
camera across the scroll path.

## Adding A Benchmark

Drop a JSON file in `benchmarks/tasks/` with `manifest`, `recipe`, optional
`baseline_recipe`, and `checks`.

After every benchmark change, regenerate the visual review pack. A release
candidate should have every `skill_plus_tools` task passing, every naive
baseline failing when present, all skill previews available, and a score delta
of at least 40 points over the baseline unless the benchmark documents a
narrower purpose. Then regenerate the blind visual eval packet. A passing
automated pack proves measurable improvement over the baseline; it is not a
substitute for saved blind human review when claiming production-grade taste or
reference fidelity.
